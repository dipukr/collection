Technical Debt

Conversation Notes  •  Software Engineering

1. What is Technical Debt?

Technical debt is the extra work you create for yourself in the future by choosing a quick or easy technical solution today instead of a better long-term solution.

You get a benefit now, but you have to pay it back later — with interest.

The idea is similar to financial debt: taking a shortcut can help you move faster today, but maintaining that shortcut can make future development slower and more expensive.

2. Simple Example

Suppose a feature needs to be delivered quickly. Instead of designing a reusable solution, the code handles each type separately: 

if (type.equals("BUYER")) {
    // logic
}

if (type.equals("SELLER")) {
    // logic
}

if (type.equals("FINANCIER")) {
    // logic
}

The code works, so the feature is released. Later, another type such as ADMIN is introduced. More conditions are added, and the same code becomes increasingly difficult to maintain.

The additional complexity and future maintenance effort represent technical debt.

4. Is Technical Debt Always Bad?

No. Taking technical debt can sometimes be a valid engineering decision.

For example:

We need to release this feature this week. We'll implement the simple solution now and refactor it next sprint.

This is intentional technical debt: the team understands the trade-off and plans to address it later.

The dangerous version is:

We'll fix it later.

If nobody ever fixes it, the temporary shortcut becomes a long-term maintenance problem.

5. Technical Debt Has “Interest”

Imagine a poorly designed stored procedure. A change may initially take only a couple of hours: 

Feature change → 2 hours

After months of accumulated complexity, the same change might require: 

Feature change
   ↓
Understand old procedure
   ↓
Understand dependencies
   ↓
Fix one query
   ↓
Fix another query
   ↓
Test unexpected side effects
   ↓
Deploy

Now the same change could take days instead of hours. That additional future cost is effectively the interest on the technical debt.

6. Examples in Software Development

In a typical backend application, technical debt can include:

  • Unoptimized SQL queries
  • Too many database calls from a single API
  • Overly complicated stored procedures
  • Duplicated Java business logic
  • Missing automated tests
  • Temporary production workarounds that remain indefinitely
  • Inconsistent error handling
  • Code that is difficult to change without causing side effects

7. Key Takeaway

Technical debt is not simply “bad code.”

It is the future cost caused by a technical decision made today.

A shortcut becomes technical debt when it creates additional maintenance, testing, debugging, performance, or development costs in the future.
