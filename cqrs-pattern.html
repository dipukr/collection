What is CQRS?

CQRS (Command Query Responsibility Segregation) separates the model that changes state from the model that reads state. Instead of one model serving both reads and writes, you build two:

  • COMMAND The write side — handles intentions to change state (CreateProduct, ChangePrice). Returns nothing (or just an id). Enforces business rules and invariants.
  • QUERY The read side — answers questions (GetProductById, SearchProducts). Returns DTOs. Has no side effects.

It grows out of the CQS principle (Bertrand Meyer): "a method should either change state or return data, but never both." CQRS applies that idea at the architectural level.

Why & When to Use It

A single model that serves both reads and writes tends to become a compromise — over-normalized for queries, or littered with read concerns that pollute the domain. CQRS is worth it when:

  • Read and write workloads have very different shapes or scale (e.g. 100:1 read/write ratio).
  • The query side needs denormalized / pre-computed views that don't match the write schema.
  • You're using Event Sourcing (CQRS is its natural companion).
  • Complex domains where task-based commands express intent better than CRUD.

Don't reach for CQRS on simple CRUD apps — the extra moving parts cost more than they return. It shines in complex, high-scale, or collaborative domains.

Benefits & Trade-offs

BenefitsTrade-offs
Read & write sides scale independently More classes and indirection
Optimized read models (denormalized, fast) Eventual consistency between models
Clear separation of concerns & intent Data duplication / sync logic
Easier to reason about business rules Higher operational complexity

Architecture

A request enters through a controller, which dispatches either a command or a query. Each goes to its own handler and its own model. The two stores may be the same database (simplest) or physically separate, kept in sync via events.

                         ┌─────────────────────┐
        write  ─────────▶ │   CommandController  │
   (POST/PUT/DELETE)      └──────────┬──────────┘
                                     │ dispatch
                                     ▼
                          ┌─────────────────────┐      ┌──────────────┐
                          │   Command Handlers   │────▶ │  WRITE MODEL │
                          │ (validate, mutate)   │      │ (normalized) │
                          └──────────┬──────────┘      └──────┬───────┘
                                     │ publishes event        │
                                     ▼                        ▼
                          ┌─────────────────────┐      ┌──────────────┐
                          │   Event Listener     │────▶ │  READ MODEL  │
                          │ (project to view)    │      │ (denormalized│
                          └─────────────────────┘      │   /  fast)   │
                                                        └──────┬───────┘
                                     ┌──────────────────────── ┘
                                     ▼
        read   ─────────▶ ┌─────────────────────┐
       (GET)              │    QueryController   │──▶ Query Handlers ──▶ DTOs
                          └─────────────────────┘

Write & Read Models

Two separate JPA entities, each tuned for its job. The write model is normalized and carries behavior; the read model is a flat, query-friendly projection.

Write Model — normalized, behavior-rich

domain/Product.java 
package com.example.catalog.domain;

import jakarta.persistence.*;
import lombok.*;
import java.math.BigDecimal;
import java.time.Instant;

@Entity
@Table(name = "products")
@Getter @NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Product {

    @Id
    private String id;

    @Column(nullable = false)
    private String name;

    @Column(nullable = false)
    private String category;

    @Column(nullable = false)
    private BigDecimal price;

    private int stock;

    private Instant updatedAt;

    public Product(String id, String name, String category,
                   BigDecimal price, int stock) {
        this.id = id;
        this.name = name;
        this.category = category;
        setPrice(price);          // funnel through invariant
        this.stock = stock;
        this.updatedAt = Instant.now();
    }

    /* ---- behavior: invariants live in the write model ---- */

    public void changePrice(BigDecimal newPrice) {
        setPrice(newPrice);
        this.updatedAt = Instant.now();
    }

    public void adjustStock(int delta) {
        if (this.stock + delta < 0)
            throw new IllegalArgumentException("Stock cannot go negative");
        this.stock += delta;
        this.updatedAt = Instant.now();
    }

    private void setPrice(BigDecimal price) {
        if (price == null || price.signum() < 0)
            throw new IllegalArgumentException("Price must be >= 0");
        this.price = price;
    }
}

Read Model — denormalized projection

readmodel/ProductView.java 
package com.example.catalog.readmodel;

import jakarta.persistence.*;
import lombok.*;
import java.math.BigDecimal;

@Entity
@Table(name = "product_view",
       indexes = {
           @Index(name = "idx_view_category", columnList = "category"),
           @Index(name = "idx_view_name",     columnList = "name")
       })
@Getter @Setter @NoArgsConstructor
public class ProductView {

    @Id
    private String id;
    private String name;
    private String category;
    private BigDecimal price;
    private int stock;

    // a precomputed, query-friendly field that the write model
    // would never store directly
    private String displayLabel;     // e.g. "Laptop — Electronics ($999.00)"
}

Command Side WRITE

Commands are immutable, intent-revealing records. Each has exactly one handler that loads the aggregate, applies the change, persists it, and publishes a domain event.

Command definitions

command/ProductCommands.java 
package com.example.catalog.command;

import jakarta.validation.constraints.*;
import java.math.BigDecimal;

/** Marker interface — every command implements it. */
public interface Command { }

public record CreateProductCommand(
        @NotBlank String name,
        @NotBlank String category,
        @NotNull @PositiveOrZero BigDecimal price,
        @PositiveOrZero int stock
) implements Command { }

public record ChangePriceCommand(
        @NotBlank String productId,
        @NotNull @PositiveOrZero BigDecimal newPrice
) implements Command { }

public record AdjustStockCommand(
        @NotBlank String productId,
        int delta
) implements Command { }

Domain event (links write → read)

command/ProductChangedEvent.java 
package com.example.catalog.command;

import com.example.catalog.domain.Product;

/** Published after any successful write so the read side can re-project. */
public record ProductChangedEvent(Product product) { }

Command handlers

command/ProductCommandHandler.java 
package com.example.catalog.command;

import com.example.catalog.domain.*;
import lombok.RequiredArgsConstructor;
import org.springframework.context.ApplicationEventPublisher;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import java.util.UUID;

@Service
@RequiredArgsConstructor
public class ProductCommandHandler {

    private final ProductRepository repository;
    private final ApplicationEventPublisher events;

    @Transactional
    public String handle(CreateProductCommand cmd) {
        Product product = new Product(
                UUID.randomUUID().toString(),
                cmd.name(), cmd.category(), cmd.price(), cmd.stock());
        repository.save(product);
        events.publishEvent(new ProductChangedEvent(product));
        return product.getId();
    }

    @Transactional
    public void handle(ChangePriceCommand cmd) {
        Product product = load(cmd.productId());
        product.changePrice(cmd.newPrice());
        events.publishEvent(new ProductChangedEvent(product));
    }

    @Transactional
    public void handle(AdjustStockCommand cmd) {
        Product product = load(cmd.productId());
        product.adjustStock(cmd.delta());
        events.publishEvent(new ProductChangedEvent(product));
    }

    private Product load(String id) {
        return repository.findById(id)
                .orElseThrow(() -> new ProductNotFoundException(id));
    }
}

Query Side READ

Queries return DTOs straight from the read model — no domain entities cross the boundary, and there are no side effects. Note the @Transactional(readOnly = true).

Query & DTO definitions

query/ProductQueries.java 
package com.example.catalog.query;

import java.math.BigDecimal;

public interface Query { }

public record GetProductByIdQuery(String id) implements Query { }
public record FindByCategoryQuery(String category) implements Query { }
public record SearchByNameQuery(String fragment)  implements Query { }

/** Read DTO returned to clients — decoupled from JPA entities. */
public record ProductDto(
        String id,
        String name,
        String category,
        BigDecimal price,
        int stock,
        String displayLabel
) { }

Query handler

query/ProductQueryHandler.java 
package com.example.catalog.query;

import com.example.catalog.domain.ProductNotFoundException;
import com.example.catalog.readmodel.*;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import java.util.List;

@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class ProductQueryHandler {

    private final ProductViewRepository views;

    public ProductDto handle(GetProductByIdQuery q) {
        return views.findById(q.id())
                .map(this::toDto)
                .orElseThrow(() -> new ProductNotFoundException(q.id()));
    }

    public List<ProductDto> handle(FindByCategoryQuery q) {
        return views.findByCategory(q.category())
                .stream().map(this::toDto).toList();
    }

    public List<ProductDto> handle(SearchByNameQuery q) {
        return views.findByNameContainingIgnoreCase(q.fragment())
                .stream().map(this::toDto).toList();
    }

    private ProductDto toDto(ProductView v) {
        return new ProductDto(v.getId(), v.getName(), v.getCategory(),
                v.getPrice(), v.getStock(), v.getDisplayLabel());
    }
}

Optional: A Simple Command/Query Bus

For larger apps you can decouple controllers from handlers with a dispatcher (a "bus") that routes each message to its registered handler. For a small service, calling the handlers directly (as in the controller below) is perfectly fine. A minimal generic gateway:

bus/Mediator.java 
package com.example.catalog.bus;

import com.example.catalog.command.*;
import com.example.catalog.query.*;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Component;
import java.util.List;

/**
 * Thin facade so callers depend on one entry point instead of
 * many handlers. Extend with a registry/reflection if you want
 * fully generic dispatch.
 */
@Component
@RequiredArgsConstructor
public class Mediator {

    private final ProductCommandHandler commands;
    private final ProductQueryHandler   queries;

    public String send(CreateProductCommand c) { return commands.handle(c); }
    public void   send(ChangePriceCommand c)   { commands.handle(c); }
    public void   send(AdjustStockCommand c)   { commands.handle(c); }

    public ProductDto       ask(GetProductByIdQuery q) { return queries.handle(q); }
    public List<ProductDto> ask(FindByCategoryQuery q) { return queries.handle(q); }
    public List<ProductDto> ask(SearchByNameQuery q)   { return queries.handle(q); }
}

REST Controller

The controller is the thinnest possible layer: translate HTTP into a command or query, dispatch, and return. Writes go through POST/PUT; reads through GET.

api/ProductController.java 
package com.example.catalog.api;

import com.example.catalog.bus.Mediator;
import com.example.catalog.command.*;
import com.example.catalog.query.*;
import jakarta.validation.Valid;
import lombok.RequiredArgsConstructor;
import org.springframework.http.*;
import org.springframework.web.bind.annotation.*;
import java.net.URI;
import java.math.BigDecimal;
import java.util.List;

@RestController
@RequestMapping("/api/products")
@RequiredArgsConstructor
public class ProductController {

    private final Mediator mediator;

    /* ---------------- WRITE (commands) ---------------- */

    @PostMapping
    public ResponseEntity<Void> create(@Valid @RequestBody CreateProductCommand cmd) {
        String id = mediator.send(cmd);
        return ResponseEntity.created(URI.create("/api/products/" + id)).build();
    }

    @PutMapping("/{id}/price")
    public ResponseEntity<Void> changePrice(@PathVariable String id,
                                            @RequestBody BigDecimal newPrice) {
        mediator.send(new ChangePriceCommand(id, newPrice));
        return ResponseEntity.noContent().build();
    }

    @PutMapping("/{id}/stock")
    public ResponseEntity<Void> adjustStock(@PathVariable String id,
                                            @RequestBody int delta) {
        mediator.send(new AdjustStockCommand(id, delta));
        return ResponseEntity.noContent().build();
    }

    /* ---------------- READ (queries) ------------------ */

    @GetMapping("/{id}")
    public ProductDto getById(@PathVariable String id) {
        return mediator.ask(new GetProductByIdQuery(id));
    }

    @GetMapping
    public List<ProductDto> list(@RequestParam(required = false) String category,
                                @RequestParam(required = false) String search) {
        if (category != null) return mediator.ask(new FindByCategoryQuery(category));
        if (search   != null) return mediator.ask(new SearchByNameQuery(search));
        return List.of();
    }
}

Exception handling

package com.example.catalog.api;

import com.example.catalog.domain.ProductNotFoundException;
import org.springframework.http.*;
import org.springframework.web.bind.annotation.*;

@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(ProductNotFoundException.class)
    public ResponseEntity<String> notFound(ProductNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(ex.getMessage());
    }

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<String> badRequest(IllegalArgumentException ex) {
        return ResponseEntity.badRequest().body(ex.getMessage());
    }
}

Syncing the Read Model (Projection)

This is the heart of CQRS: after every successful write, the read model must be updated. Here an event listener rebuilds the ProductView from the changed aggregate. We use AFTER_COMMIT so the projection only runs once the write transaction has safely committed.

readmodel/ProductProjection.java 
package com.example.catalog.readmodel;

import com.example.catalog.command.ProductChangedEvent;
import com.example.catalog.domain.Product;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.*;
import org.springframework.transaction.event.TransactionalEventListener;
import org.springframework.transaction.event.TransactionPhase;

@Component
@RequiredArgsConstructor
public class ProductProjection {

    private final ProductViewRepository views;

    /**
     * Runs after the write transaction commits, in its own transaction.
     * In a distributed setup this listener would instead consume a
     * message from Kafka/RabbitMQ and could live in a separate service.
     */
    @Async
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void on(ProductChangedEvent event) {
        Product p = event.product();

        ProductView view = views.findById(p.getId())
                .orElseGet(ProductView::new);

        view.setId(p.getId());
        view.setName(p.getName());
        view.setCategory(p.getCategory());
        view.setPrice(p.getPrice());
        view.setStock(p.getStock());
        // precompute the denormalized field the read side serves
        view.setDisplayLabel(
            "%s — %s ($%s)".formatted(p.getName(), p.getCategory(), p.getPrice()));

        views.save(view);
    }
}

Enable async listeners with @EnableAsync on a @Configuration class (or the main application class).

CatalogApplication.java

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication

    public static void main(String[] args) {
        SpringApplication.run(CatalogApplication.class, args);
    }
}

Practical Tips

  • Start simple. Begin with one database and in-process events (as above). Split stores only when scale demands it.
  • Embrace eventual consistency. The read model may lag the write model by milliseconds. Design the UI/API to tolerate it (e.g. return the created id and let the client poll, or read from the write side immediately after a write).
  • Commands return little. Ideally void or just an id — not the full object.
  • Queries never mutate. Keep them readOnly and side-effect free.
  • One handler per command. Keeps responsibilities crisp and testable.
  • CQRS ≠ Event Sourcing. They pair well but are independent. You can do CQRS with plain JPA, as shown here.
  • For heavy lifting consider the Axon Framework, which provides a command bus, query bus, event store, and sagas out of the box.
