What is VPN and how it works. Explain it in deep details.

AI

A VPN (Virtual Private Network) creates an encrypted tunnel between your device and another computer (called a VPN server). Instead of sending your internet traffic directly to websites, your traffic first goes through the VPN server.

Think of it as sending your mail to a trusted forwarding office in another city. The forwarding office then sends the mail to the final destination. Anyone watching your local mailbox only sees that you sent mail to the forwarding office, not the final recipient.

  1. Browser asks DNS: What is the IP address of google.com?
  2. DNS replies: 142.250.193.110
  3. Browser connects: Your PC → Google Server

Step-by-Step Packet Journey

Suppose: Your PC 192.168.1.10, Router 192.168.1.1, Public IP 49.205.88.101, VPN Server 45.100.120.50, Google 142.250.xxx.xxx.

Without VPN, Google receives Source IP 49.205.88.101.

With VPN, your PC first encrypts everything. It creates an encrypted packet whose destination is the VPN server. Only the VPN server can decrypt it. So the ISP only sees an encrypted tunnel to the VPN server — it cannot see Google, Facebook, or YouTube (if the VPN tunnels DNS and traffic through itself). The VPN decrypts the packet and forwards it to Google, which thinks the request came from the VPN server.

What is an Encrypted Tunnel?

A tunnel is not a physical cable — it is a logical encrypted connection. Imagine putting a letter inside a normal envelope (everyone can read the address) versus a steel box (only the VPN server has the key). The ISP sees only encrypted data: not login credentials, visited pages, or downloaded files (if the traffic itself is encrypted, such as HTTPS).

What Happens During a VPN Connection?

  1. Connect: VPN client contacts server with a "Hello".
  2. Authentication: Username, password, certificate, or token — server verifies identity.
  3. Key Exchange: Client and server generate a shared secret using Diffie-Hellman or ECDH. They derive the same shared key without ever sending the secret over the network. An eavesdropper sees only public values and cannot feasibly compute the shared secret.
  4. Create Session Keys: e.g. AES-256 key, HMAC key, IV.
  5. Virtual Network Interface: The VPN software creates a virtual adapter (Windows VPN Adapter, or Linux tun0/tap0). Traffic now routes through this virtual interface.

Encapsulation

An original packet [IP Header][TCP Header][HTTP Data] becomes [Outer IP Header][VPN Header][Encrypted Payload]. This is called encapsulation. At the VPN server, the outer header is removed, the payload decrypted, and the original packet is sent to Google. Google's reply is encrypted and sent back the same way.

DNS Leak

Without a VPN, DNS requests go to the ISP's DNS, so the ISP knows every website. Good VPNs send DNS through the tunnel (Encrypted → VPN DNS → Website), so there is no DNS leak.

IP Address Changes

Without VPN your IP is e.g. 49.xxx.xxx.xxx; after VPN it appears as 45.xxx.xxx.xxx. Websites think you're located where the VPN server is.

Split Tunnel vs Full Tunnel

Split tunneling: only some traffic (e.g. office software) goes through the VPN, while Netflix uses the normal internet. Full tunneling: everything goes through the VPN — more secure but may reduce speed since all traffic is routed through the VPN.

Types of VPN

  1. Remote Access VPN — for employees connecting to an office network.
  2. Site-to-Site VPN — connects two offices (e.g. Delhi ↔ Mumbai) so they appear as one network.
  3. Personal VPN — consumer services (e.g. NordVPN, ExpressVPN, Proton VPN) to hide IP, protect on public Wi-Fi, and access region-specific services (subject to terms of use).

VPN Protocols

  • OpenVPN — open source, very secure, uses TLS for key exchange and authentication, UDP or TCP, widely supported.
  • WireGuard — newest major protocol: smaller codebase, faster, modern cryptography, easier to audit; often faster than OpenVPN due to less overhead.
  • IPsec/IKEv2 — common in enterprises; good for mobile devices and stable reconnection when switching between Wi-Fi and cellular.

Encryption Algorithms

  • AES-256 — symmetric encryption (same key to encrypt and decrypt); widely used and very secure when implemented correctly.
  • ChaCha20 — used by WireGuard; often performs well on devices without dedicated AES hardware acceleration.

Authentication

A VPN ensures packets were not modified, using methods such as HMAC and Poly1305. If even one bit changes, the packet is rejected.

Does VPN Make You Anonymous?

No. It provides privacy, not complete anonymity. Websites can still identify you via logged-in accounts, browser fingerprinting, cookies, device information, and behavior patterns. The VPN provider itself can potentially see traffic metadata or even content for non-HTTPS connections — choosing a trustworthy provider matters.

Performance Impact

Speed may decrease due to encryption/decryption work, extra routing through the VPN server, distance to the server, and server load. Modern protocols like WireGuard can reduce this overhead.

Summary

A VPN works by authenticating you with a server, negotiating encryption keys securely, creating a virtual network interface, encapsulating and encrypting your packets, sending traffic through an encrypted tunnel, decrypting it at the VPN server and forwarding it, then returning responses through the same tunnel. Your ISP sees only an encrypted connection to the VPN server, while websites see the VPN server's IP instead of yours. This improves privacy and secures untrusted networks, but does not provide complete anonymity.

To really understand VPNs, you need to understand what happens at every layer of the networking stack. Let's follow a single request (opening https://www.google.com) in two scenarios.

Scenario 1: WITHOUT VPN

+-------------------+
| Your Laptop       |  IP: 192.168.1.10
+---------+---------+
          |
+---------v---------+
| Home Router       |  LAN:192.168.1.1  WAN:49.205.88.101
+---------+---------+
          |
+---------v---------+
| ISP               |
+---------+---------+
          |
+---------v---------+
| Internet          |
+---------+---------+
          |
+---------v---------+
| Google Server     |  142.250.xxx.xxx
+-------------------+
  1. You type https://www.google.com — browser needs Google's IP.
  2. DNS Lookup: "What is the IP of google.com?" → 142.250.193.110.
  3. Browser creates HTTP request: GET /, Host: google.com (not sent yet).
  4. TLS (HTTPS): browser performs a TLS handshake → shared encryption key. The request becomes an encrypted HTTP request that nobody between you and Google can read.
  5. TCP Layer: adds TCP header (Source Port 51525, Destination Port 443).
  6. IP Layer: OS adds IP header (Source 192.168.1.10, Destination 142.250.193.110).
  7. Ethernet/WiFi Layer: OS wraps with a MAC header and sends to the router.
  8. Router: removes MAC header, reads destination IP, performs NAT — rewriting source 192.168.1.10 → 49.205.88.101 (private IPs can't travel on the public Internet).
  9. ISP: sees Source 49.205.88.101 → Destination 142.250.193.110. Payload is encrypted, so they can't read your search — but they know you connected to Google, when, and how much data.
  10. Internet Routers: forward by destination IP; they don't care about encrypted contents.
  11. Google: receives Source IP 49.205.88.101 and replies; the response travels back the same way.
DeviceCan see
LaptopEverything
RouterDestination IP
ISPDestination IP, your public IP, timing, traffic size
Internet routersSource and destination IP
GoogleYour public IP and decrypted HTTPS content

Scenario 2: WITH VPN

VPN Server IP 45.100.120.50. Now Google is not the first destination anymore.

  1. Connect VPN — VPN software starts.
  2. Client contacts VPN server ("Hello").
  3. Authentication: username, password, certificate, token — server verifies you.
  4. Key Exchange: Diffie-Hellman / ECDH → shared secret → AES key, authentication key, session keys.
  5. Virtual Network Adapter: OS creates a VPN interface; apps now use it as the preferred route.
  6. Browser wants Google: creates GET /, HTTPS still encrypts it — nothing changes here.
  7. Original packet: Source 10.8.0.2 (internal IP assigned by the VPN), Destination Google — but not sent directly.
  8. VPN intercepts packet: captures it and encrypts the entire packet → [VPN Header][Encrypted Original Packet].
  9. New Outer IP Header: Source 49.205.88.101, Destination 45.100.120.50. Google disappears from view — final packet is [Outer IP Header][VPN Header][Encrypted Original Packet] (encapsulation).
  10. Router: forwards to the VPN server; no idea Google is inside.
  11. ISP: sees only Source 49.205.88.101 → Destination 45.100.120.50, payload encrypted random bytes. Cannot see Google, Facebook, YouTube, Gmail (provided DNS is also tunneled).
  12. VPN server receives packet: decrypts with the key → original packet's destination (Google) appears.
  13. VPN server sends to Google: Source 45.100.120.50, Destination Google. Google thinks the user IP is 45.100.120.50 — your real IP is hidden.
  14. Google replies to 45.100.120.50; VPN server encrypts it and sends it back through the tunnel; your laptop decrypts; browser displays Google.

Two Layers of Encryption

A VPN does not replace HTTPS. With HTTPS over VPN there are two separate layers:

+------------------------------------------------+
| VPN Encryption (Laptop <-> VPN Server)         |
|   +----------------------------------------+   |
|   | HTTPS Encryption (Laptop <-> Google)    |  |
|   |   HTTP Request                          |  |
|   +----------------------------------------+   |
+------------------------------------------------+
  • Inner layer (HTTPS): protects data all the way to Google; the VPN server cannot decrypt it.
  • Outer layer (VPN): protects traffic between your device and the VPN server; the ISP can't see which sites you visit.

So visiting https://www.google.com through a VPN: your ISP only sees the VPN connection; the VPN server sees you're connecting to Google but cannot read the HTTPS contents; Google sees the VPN server's IP.

How does VPN software intercept packets? Please explain with C/Java code. Is there any Linux syscall related to this?

AI

VPN software does not "magically intercept" packets. It asks the OS to route packets to a virtual network interface (TUN/TAP). The OS sends packets there instead of to the physical network card. The VPN program reads packets from that virtual interface, encrypts them, and sends them through a normal socket. There is no single Linux syscall called intercept_packet().

High-Level Architecture

Without VPN:                With VPN:
Application (Chrome)        Application
     |                          |
TCP/IP Stack               TCP/IP Stack
     |                          |
eth0 (Network Card)        tun0 (Virtual Interface)
     |                          |
Internet                   VPN Process -> Encrypt -> Socket -> eth0 -> Internet

The kernel sends packets to tun0, not eth0, and the VPN process simply reads packets from tun0.

What is TUN?

Linux provides a virtual device called TUN — a "fake network card". The kernel thinks it's sending a packet to a network interface, but instead the packet becomes readable by a userspace program.

How VPN Creates TUN

The kernel exposes /dev/net/tun. The VPN opens it like a file:

int fd = open("/dev/net/tun", O_RDWR);

struct ifreq ifr;
memset(&ifr, 0, sizeof(ifr));
ifr.ifr_flags = IFF_TUN | IFF_NO_PI;
strcpy(ifr.ifr_name, "tun0");
ioctl(fd, TUNSETIFF, &ifr);

This creates tun0, verifiable with ip addr (e.g. tun0: inet 10.8.0.2).

Routing Table Changes

Without VPN: default via 192.168.1.1 dev eth0 (everything → eth0). When the VPN connects: default via 10.8.0.1 dev tun0 (everything → tun0). Chrome doesn't know this changed — it just writes data to TCP.

VPN Reads / Encrypts / Sends

while (1) {
    int n = read(tun_fd, packet, sizeof(packet));  // entire IP packet
    encrypt(packet);
    send(socket_fd, packet, n, 0);
}

The VPN opens a normal socket — socket(AF_INET, SOCK_DGRAM, 0) for UDP (WireGuard) or SOCK_STREAM for TCP (OpenVPN supports both).

Receiving Data

When encrypted packets arrive, the VPN decrypts and writes back into TUN:

decrypt(packet);
write(tun_fd, packet, length);

The kernel then receives the packet as if a network card delivered it, and passes it up: IP → TCP → Chrome. Chrome never knows a VPN exists.

Complete VPN Loop

while (1) {
    int len = read(tun_fd, packet, sizeof(packet));   // outgoing packet
    encrypt(packet);
    send(sock, packet, len, 0);                        // to VPN server
    len = recv(sock, packet, sizeof(packet), 0);       // encrypted response
    decrypt(packet);
    write(tun_fd, packet, len);                        // inject back into kernel
}

Java Example

Java cannot directly manipulate /dev/net/tun with only the standard library. Three options: (1) JNI to call native C, (2) JNA to invoke Linux syscalls, (3) a native helper process that owns the TUN interface.

TunDevice tun = TunDevice.open();
DatagramSocket socket = new DatagramSocket();

while (true) {
    byte[] packet = tun.read();
    byte[] encrypted = encrypt(packet);
    socket.send(new DatagramPacket(encrypted, encrypted.length, vpnServer));
}

The actual TunDevice.open() implementation is native C.

Which Linux Syscalls Are Used?

SyscallPurpose
open()Open /dev/net/tun
ioctl()Create/configure the TUN interface (TUNSETIFF)
read()Read packets from the TUN device
write()Inject packets back into the kernel
socket()Create a UDP/TCP socket to the VPN server
send() / sendto()Send encrypted packets
recv() / recvfrom()Receive encrypted packets
poll() / epoll_wait() / select()Wait efficiently on both TUN and the socket
setsockopt()Configure socket behavior (timeouts, buffers)

Packet interception itself is not a syscall — it's the combination of creating a virtual interface, updating the routing table, and reading packets from that interface in userspace.

How WireGuard Does It

Chrome -> TCP/IP Stack -> tun0 -> read() -> WireGuard
       -> ChaCha20-Poly1305 -> UDP socket -> Internet -> WireGuard Server

OpenVPN, WireGuard, and others use the same fundamental idea; differences are in encryption, key exchange, and protocol design — not in how packets are captured.

Client — vpn_client.c

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <fcntl.h>
#include <string.h>
#include <linux/if_tun.h>
#include <linux/if.h>
#include <sys/ioctl.h>
#include <sys/socket.h>
#include <arpa/inet.h>

#define PORT 5555

int tun_create(char *dev) {
    struct ifreq ifr;
    int fd = open("/dev/net/tun", O_RDWR);
    memset(&ifr, 0, sizeof(ifr));
    ifr.ifr_flags = IFF_TUN | IFF_NO_PI;
    strcpy(ifr.ifr_name, dev);
    ioctl(fd, TUNSETIFF, &ifr);
    return fd;
}

int main() {
    char packet[2000];
    int tun  = tun_create("tun0");
    int sock = socket(AF_INET, SOCK_DGRAM, 0);

    struct sockaddr_in server;
    server.sin_family = AF_INET;
    server.sin_port   = htons(PORT);
    inet_pton(AF_INET, "192.168.1.100", &server.sin_addr);

    while (1) {
        int n = read(tun, packet, sizeof(packet));
        sendto(sock, packet, n, 0,
               (struct sockaddr*)&server, sizeof(server));
    }
}

int main() {
    char packet[2000];
    int tun  = tun_create("tun0");
    int sock = socket(AF_INET, SOCK_DGRAM, 0);

    struct sockaddr_in server;
    server.sin_family      = AF_INET;
    server.sin_port        = htons(PORT);
    server.sin_addr.s_addr = INADDR_ANY;

    bind(sock, (struct sockaddr*)&server, sizeof(server));

    while (1) {
        int n = recv(sock, packet, sizeof(packet), 0);
        write(tun, packet, n);
    }
}

The VPN program is just copying bytes: read(tun) → send(socket) and recv(socket) → write(tun). That is the fundamental mechanism behind a VPN.

What is missing?

  • Bidirectional forwarding — both sides must send and receive in both directions.
  • I/O multiplexing — select()/poll()/epoll() to handle TUN and socket in one thread.
  • Encryption & authentication — otherwise anyone can read/modify packets.
  • Client authentication — only authorized clients connect.
  • Routing/forwarding — enable net.ipv4.ip_forward=1 and configure NAT.
  • MTU handling — encapsulation grows packets; avoid fragmentation.
  • Error handling — check all return values.
  • Connection management — keepalives, reconnection, replay protection.

The goal of Stage 1 is not to send packets anywhere. We only want to: create a TUN interface, configure an IP address, route some traffic into it, read every packet from the kernel, and print the raw bytes in hex.

Chrome -> TCP/IP Stack -> Routing Table -> tun0 -> read() -> Our Program -> printf("%02X")

Our program becomes the "network card".

Step 1 — How the kernel delivers packets

With a TUN interface, when the kernel wants to send an IP packet through tun0, it stores it in the TUN device, and a blocking read() returns that packet to your program.

Step 2 — Create the TUN interface

#include <stdio.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <linux/if.h>
#include <linux/if_tun.h>
#include <sys/ioctl.h>

int createTun(char *name) {
    struct ifreq ifr;
    int fd = open("/dev/net/tun", O_RDWR);
    if (fd < 0) { perror("open"); return -1; }

    memset(&ifr, 0, sizeof(ifr));
    ifr.ifr_flags = IFF_TUN | IFF_NO_PI;
    strcpy(ifr.ifr_name, name);

    if (ioctl(fd, TUNSETIFF, &ifr) < 0) {
        perror("ioctl");
        close(fd);
        return -1;
    }
    return fd;
}

open("/dev/net/tun", O_RDWR) does not create the interface — it just opens the Linux TUN driver. The ioctl(fd, TUNSETIFF, &ifr) call tells the kernel to create a virtual interface named tun0, exactly as if a new network card had been plugged in.

Step 3 — Main loop

int main() {
    char packet[2000];
    int tun = createTun("tun0");

    while (1) {
        int len = read(tun, packet, sizeof(packet));
        printf("Received packet (%d bytes)\n", len);

        for (int i = 0; i < len; i++) {
            printf("%02X ", (unsigned char)packet[i]);
            if ((i + 1) % 16 == 0) printf("\n");
        }
        printf("\n\n");
    }
}

There is no networking code yet — just read().

gcc tun.c -o tun
sudo ./tun   # root required to create TUN devices

Initially nothing happens, because no packets are being routed to tun0 yet.

Step 7 — Generate traffic

ping 10.0.0.2

The kernel constructs an ICMP Echo Request [IP Header][ICMP Header][Payload] and writes it to tun0. Our blocked read() returns immediately with the packet.

Step 8 — Example output

45 00 00 54
1A 2B 40 00
40 01
...

This is the raw IPv4 packet.

Step 9 — Decode the first bytes

Suppose the packet starts with 45 00 00 54:

  • Byte 0 = 0x45 → nibbles 4 | 5. Upper nibble 4 = IPv4; lower nibble 5 = 5 × 4 = 20-byte header.
  • Bytes 00 54 = 0x0054 = 84 → total IP packet length = 84 bytes.
  • Protocol field: 01 = ICMP, 06 = TCP, 11 = UDP.

Step 10 — Parse the IP header

#include <netinet/ip.h>

struct iphdr *ip = (struct iphdr *)packet;
printf("Version      : %d\n", ip->version);
printf("Header Length: %d\n", ip->ihl * 4);
printf("Protocol     : %d\n", ip->protocol);
printf("TTL          : %d\n", ip->ttl);
printf("Packet Length: %d\n", ntohs(ip->tot_len));

#include <arpa/inet.h>
struct in_addr src, dst;
src.s_addr = ip->saddr;
dst.s_addr = ip->daddr;
printf("Source      : %s\n", inet_ntoa(src));
printf("Destination : %s\n", inet_ntoa(dst));

What you've learned

  • open("/dev/net/tun") opens the TUN driver.
  • ioctl(TUNSETIFF) creates the virtual interface.
  • The kernel routes packets to tun0 per the routing table.
  • read() returns complete IP packets to your program.
  • Your program can inspect, modify, encrypt, forward, or drop those packets.

This is the fundamental mechanism on which OpenVPN and many userspace VPNs are built. The next stage: take each packet read from tun0 and send it over a UDP socket to another machine, then write received packets back into tun0 on the other side.
